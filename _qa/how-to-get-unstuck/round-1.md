# スライド設計: 詰まったときの動き方

対象ファイル: `cs/how-to-get-unstuck.html`

使い方: 各質問の「**回答:**」に書き込んでください。推奨でよければ `OK` だけで結構です。
書き終わったら「終わった」と伝えてください。このディレクトリを読みに行きます。

前提（CLAUDE.md で既に決まっていること）:
- 中身は **エラーの読み方・検索の仕方・ChatGPT への聞き方** の3本柱
- 全分野のスライドからここにリンクする
- 「よくあるエラー一覧」は作らない。生徒が実際に質問してきた内容は各スライドの注意書きに足す

## ラウンド 1

### ❓ Q1 —【最重要】これは読み物か、授業スライドか

同じ内容でも、この選択で**枚数も文章の長さも全く変わります。**

- **A. 1ページの読み物**（`_template/sample-lesson.html`）← 推奨
  詰まった瞬間に開いて、必要なところだけ拾い読みする参照ページ。
  早見表と同じ形。スクロールして全体を見渡せるので「いま自分はどの段階か」が分かる。
  弱点: 授業で頭から読ませるには向かない。

- **B. 授業スライド1コマ**（`_template/slide-template.html`、35〜40枚）
  1画面ずつ送りながら、90分かけて「詰まり方」そのものを教える。
  エラーを実際に出させて読ませる演習ができる。
  弱点: 詰まった生徒がその場で開いて探すには、送るのが面倒。

- **C. 両方つくる**
  授業スライド1本 ＋ 参照用の1ページ。Unix でやったのと同じ二段構え。
  弱点: いま作るのは2本になる。

➡️ **推奨: A（1ページの読み物）**
このページの価値は「授業で教わったこと」ではなく、**困った瞬間に開けること**にあります。
1コマ使って教えるほどの分量が本当にあるかは、Aを作ってから判断できます。
Aを先に作れば、あとでBに膨らませるのは楽です（逆は面倒）。

**回答:** Aです

### ❓ Q2 — 例に使う環境をどれにするか

「エラーの読み方」は、画面に出るものが環境ごとに違うため、**具体例なしでは書けません。**
しかしこのページは4分野すべてからリンクされます。

- **A. Python（Colab）の画面を主役にして、他は考え方だけ** ← 推奨
  いま生徒が最初に触るのが Python なので、実物の例はすべて Colab で出す。
  Java / Unity については「出る場所は違うが、読み方は同じ」と1行だけ触れる。
- **B. 4分野それぞれの例を並べる**
  Colab のエラー、Java のスタックトレース、Unity の Console、ターミナル。
  正確だが、いま Python しか触っていない生徒には情報が多すぎる。
- **C. 環境に依存しない書き方だけにする**
  「赤い字が出たら落ち着く」「メッセージを検索する」という原則のみ。
  どの分野でも古びないが、**薄くなって役に立たない**恐れがある。

➡️ **推奨: A**
実物が1つも無いと、生徒は自分の画面と結びつけられません。
まず Python で「読める」経験を作り、他分野は各スライド側で補うのが現実的です。

**あわせて確認**: Java / Spring Boot と Unity は、生徒はもう触っていますか。
それとも Python が最初ですか。ここで A か B かが変わります。

**回答:** Aでもよいですが、生徒によってPythonを触っていたり、Javaを触っていたり、なんならJavaやってることはEclipseでWebアプリの制作だしで生徒によってバラバラです。

### ❓ Q3 — エラーの読み方をどこまで踏み込むか

ここは**言語によって読む向きが逆**なので、雑に書くと嘘になります。

- Python のトレースバックは、**いちばん下**にエラーの種類とメッセージが出ます
- Java の例外は、**いちばん上**にメッセージが出て、下に長い呼び出し履歴が続きます

- **A. 「最後の1行」と「矢印の行」の2か所だけ教える** ← 推奨
  Python に限定した、いちばん単純な読み方。中学生でも今日から使える。
  他言語については「出る場所が違うことがある」とだけ注意書きを置く。
- **B. トレースバック全体の構造を教える**
  どの行がどのファイルの何行目か、自分のコードとライブラリの境目はどこか。
  読み方としては正しいが、初学者には重い。
- **C. エラーの種類（NameError / TypeError など）を意味とセットで教える**
  ただし CLAUDE.md の「よくあるエラー一覧は作らない」に抵触しないか、線引きが必要です。
  **「一覧表にはしないが、名前の読み方だけ書く」なら両立できます**（例: `〜Error` の前半が
  何が起きたかを表している、という説明だけ置く）。

➡️ **推奨: A**
まず「全部読まなくていい」と伝えることが、いちばん効きます。
量に圧倒されて読まずに手を挙げる、が実際いちばん多い詰まり方です。

**回答:** Aで

### ❓ Q4 — ChatGPT の使い方をどう位置づけるか

これは**教室の方針**なので、私では決められません。書き方が根本から変わります。

- **A. 答えを聞いてよい。ただし「動いた理由」を説明できることを条件にする**
  実務に近い。生徒は速く進める。
  書くこと: エラー全文の貼り方、自分のコードの添え方、「なぜそうなるか説明して」の付け方。
- **B. 答えのコードはもらわない。ヒントまでにする**
  「直したコードを書かないで、どこが間違っているかだけ教えて」と頼ませる。
  考える力は残るが、生徒がその制約を守るかは自己申告になる。
- **C. まず自分で試してから使う（時間で区切る）**
  例: 5分自分で試す → 検索 → それでもだめなら ChatGPT。
  順番だけ決めて、使い方自体は制限しない。

➡️ **推奨: C ＋ A の書き方**
禁止は守られません。それより「**聞く前にこれをやる**」の順番を決めるほうが機能します。
そのうえで、聞くときの貼り方（エラー全文＋自分のコード＋やりたいこと）を教える。

**あわせて確認**: 提出物や課題で「ChatGPT を使ったら書く」などのルールはありますか。

**回答:** 推奨の方法かな

### ❓ Q5 — 人に聞くまでのラインを決めるか

「先生を呼んでいいタイミング」が書いてあると、生徒は動きやすくなります。
1クラス10人以下なので、全員が同時に手を挙げても回れる規模ではあります。

- **A. 時間で区切る** — 「10分やってだめなら呼ぶ」← 推奨
- **B. 手順で区切る** — 「①エラーを読む ②検索 ③ChatGPT、ここまでやって呼ぶ」
- **C. 書かない** — いつでも呼んでよい

➡️ **推奨: A と B を組み合わせて1行にする**
「**10分**、または①②③をやってから呼ぶ」。時間だけだと粘りすぎる生徒が出ます。

**何分にしますか。** 授業が90分なので、10分は長すぎるかもしれません。

**回答:** 推奨で。ただし前提として、**質問できる相手が常にそばにいるとは限らない**ものとして書いてほしい。生徒だけで前に進めることを優先。

### ❓ Q6 — スクリーンショットは使うか

**私には撮れません。** 必要ならユーザーに撮っていただく必要があります。

- **A. 使わない** ← 推奨
  エラーの実物は、コードブロックに文字として載せる（`.out` の枠が使えます）。
  Colab の見た目が変わっても古びない。画像の管理も要らない。
- **B. Colab のエラー表示を1〜2枚だけ撮ってもらう**
  「赤い枠のここを見る」と矢印で示せる。初学者への効果は大きい。
  必要なもの: わざとエラーを出した Colab のセルの画面。

➡️ **推奨: A**
エラーの文面はテキストで載せたほうが、生徒がコピーして検索できます。
それがこのページで教えたいこと（検索・貼り付け）と一致します。

**回答:** 使わんでいいよ

### ❓ Q7 — このページはどこからリンクされるか

CLAUDE.md には「全スライドからリンク」とあります。実際の運用を確認させてください。

- **A. 各スライドの末尾に「うまく動かないときは」の囲みを置いてリンク** ← 推奨
  テンプレートに `.note.stuck` が既にあります。まさにこの用途です。
- **B. トップの `index.html` にも独立したカードとして載せる**
  分野に属さないので、置くなら「共通」のような枠が要ります。
- **C. 両方**

➡️ **推奨: C**
各スライドからは A の囲みで、トップにも1枚カードを置く。
生徒が「あのページどこだっけ」となったとき、トップから辿れる必要があります。

**なお**: `python/python-cheatsheet.html` は現在このページが無いためリンクを張っていません。

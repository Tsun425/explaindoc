### ❓ Q9 — Lombok の `@RequiredArgsConstructor` をどこまで説明するか

サンプルのDIは、PDFの図と**見た目が違います**。

```java
// サンプル（RegistServiceImpl）
@Service
@RequiredArgsConstructor
public class RegistServiceImpl implements RegistService {
    private final RegistRepository repository;   // ← これでDIされている
```

`@Autowired` がどこにも書いていないので、**「で、どこでDIしてるの？」**が
必ず引っかかります。

- **A. サンプル通り Lombok 版だけを教える** ← 推奨
  「`final` のフィールドを書くと、Lombok がコンストラクタを自動で作り、
  Spring がそこに入れてくれる」と1枚使って説明する。
  生徒が実際に書いているコードと一致します。
  弱点: 「Lombokの魔法」がもう1段増える。

- **B. `@Autowired` 版を先に見せてから Lombok 版に移る**
  PDFやネットの記事は `@Autowired` で書かれているものが多いので、
  検索したときに読めるようになる。
  弱点: 2枚〜3枚増える。書かないコードを教えることになる。

- **C. Lombok を展開したコンストラクタを1枚だけ併記する**
  `@RequiredArgsConstructor` が実際に生成しているものを見せる。
  「魔法ではない」ことだけ示して、`@Autowired` の話はしない。

➡️ **推奨: A + C。** Lombok版を主役にしつつ、**展開後のコンストラクタを1枚だけ**見せます。
`@Autowired` は「検索するとこう書いてある記事が多いが、同じことをしている」と
注意書き1行で触れるにとどめます。生徒が1人なので、脱線は最小にしたいです。

**回答:** これ前回のセクションでまなんだので、説明する必要ないかも、サンプル通りにとりあえずいきましょう

### ❓ Q10 — `entity` と `form` はどの層だと教えるか

サンプルには `Review`（entity）と `ReviewRegistForm`（form）があります。
**PDFの3層図には出てきません。** でも生徒は必ず「これはどの層？」と思います。

- **A. 「層をまたいで運ばれるデータの入れ物」として、3層の外に描く** ← 推奨
  Controller → Service → Repository と**受け渡されていく荷物**で、
  どれかの層に属する部品ではない、と教える。図では3層の横に細長く置きます。
  サンプルでも `Review` は Controller で作られて Repository まで運ばれています。

- **B. `form` はプレゼン層、`entity` はインフラ層に属すると教える**
  置き場所としてはすっきりします。
  弱点: `Review` を Controller が `new` している事実と食い違います。

- **C. 今回は触れない。次回のDBの回で扱う**
  レイヤの話に集中できます。
  弱点: パッケージのツリーを見せた瞬間に質問が出ます。

➡️ **推奨: A。** ついでに **「なぜ form と entity が別物なのか」**（画面の都合と
保存の都合は違う）に1枚使うと、Controller にある詰め替えのコードが腑に落ちます。

**回答:** 任せるけどなんにせよ正しい情報を教えたい。

### ❓ Q11 — 「次回DBに繋ぐ」を、疎結合の御利益の実演に使うか

`RegistRepositoryImpl` は今こうなっています。

```java
@Repository
public class RegistRepositoryImpl implements RegistRepository {
    @Override
    public void add(Review review) {
        System.out.println("---登録---");
        System.out.println(review);
    }
}
```

**DBに繋がっていません。**画面に出さず、コンソールに出しているだけです。
そして次のセクションでDBを学ぶ予定、とのことでした。

これは**疎結合の説明にこれ以上ない実例**だと思います。
「DBがまだ無くても、画面と業務処理は完成させられる。
次回このクラスの中身だけ書き換えれば本物になる。**他のファイルは1行も触らない**」

- **A. 第4章の締めに、この実演を2枚使って置く** ← 推奨
  疎結合が「テストや将来のため」の抽象論ではなく、
  **いま自分のプロジェクトで実際に効いている**ことを見せられます。
  次回への橋渡しにもなります。

- **B. 触れない**
  レイヤの原則の説明に集中する。

➡️ **推奨: A。** これが無いと第4章は「そういうものらしい」で終わります。
`RegistServiceImpl` も `ReviewController` も、DB対応で**変更ゼロ**である、
というところまで明示します。

**回答:** とりあえずAで
